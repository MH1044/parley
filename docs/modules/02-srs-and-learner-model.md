# 02: SRS and learner model

## Goal

The core knows what the learner knows. Items from the syllabus become FSRS cards; every review is
logged and scheduled; skill mastery and states drive the learning path; an adaptive placement test
of 12 to 20 questions estimates where to start and a CEFR level. All of it is deterministic and
offline.

## Scope

- Migration `0001_init.sql` with the tables `meta`, `courses`, `skills`, `items`,
  `accepted_answers`, `cards`, `review_log` of `docs/ARCHITECTURE.md` §4; `PRAGMA user_version`;
  the two store errors below.
- `Store::start_course(syllabus, forms, now)`: inserts skills and items idempotently; a new
  syllabus version marks removed items `retired` and keeps their cards and log.
- Two cards per item (`receptive`, `productive`), created `new` when the item is introduced.
- `schedule(card, rating, now)` through the `fsrs` crate with its default parameters, desired
  retention from settings (0.80 to 0.95, default 0.90), no fuzz, maximum interval 365 days.
- The rating mapping from a graded outcome (table in Design notes).
- An append-only review log and `replay(log) -> cards`.
- Retrievability now, the due queue (most at risk first), skill mastery and skill states.
- Placement: the staircase in Design notes, its CEFR label, and tested-out skills.
- Local date from the injected clock; a seeded random source (SplitMix64) for simulations.
- CLI: `parley srs replay <log.json> [--retention r] [--json]`, `parley placement simulate
  --syllabus <file> --boundary <n> [--slip p] [--seed s] [--json]`.
- Fixture: `syllabus-mini`, generated by `parley-fixtures` (shape in Design notes).

Errors: `StoreError::Migration(n)` displays "Parley could not update its data file (step {n}).
Restore a backup or report this."; `StoreError::TooNew(v)` (a newer `user_version` than the build
knows) displays "This data file was written by a newer Parley. Update Parley to open it.";
`UnknownItem(id)` displays `unknown item {id}`; `UnknownSkill(id)` displays `unknown skill {id}`;
`Sqlite(message)` displays the message.

CLI (one JSON object on stdout; `--json` is accepted and changes nothing; usage errors exit 2 with
one line on stderr and nothing on stdout, in module 01's wording):

    parley srs replay <log.json> [--retention <r>] [--json]
        log.json: {"schema": "parley.review-log/1", "entries": [ReviewLogEntry, ...]}; in an entry,
        elapsed_days, stability_after and difficulty_after are optional and ignored (recomputed),
        response_ms may be null or absent. --retention defaults to 0.90.
        → {"cards": [Card, ...]}   (replay's order; a Card serialises its nine fields in the order
          above, null for an empty Option)
        Usage errors: `error: <log.json> is required. Run parley --help.`, `error: {path} not found`,
        `error: --retention must be a number from 0.80 to 0.95. Run parley --help.`
        A file that is not a review log: exit 1, `error: {path}: {parser message}` on stderr.
    parley placement simulate --syllabus <file> --boundary <n> [--slip <p>] [--seed <s>] [--json]
        A simulated learner who answers correctly exactly at skill indices below <n>, each answer
        flipped with probability <p> (default 0) drawn from SplitMix64(<s>) (default seed 0).
        → {"skills": N, "questions": [i], "answers": [bool], "reversals": [i], "estimate": i,
           "label": "...", "tested_out": [skill_id]}
        Usage errors: `error: --syllabus is required. Run parley --help.`, the same for --boundary,
        `error: {path} not found`, `error: --boundary must be a whole number. Run parley --help.`,
        `error: --slip must be a number from 0 to 1. Run parley --help.`,
        `error: --seed must be a whole number. Run parley --help.`
        A syllabus that does not load: exit 1 and the load errors as `content validate --json`
        prints them (`{"ok": false, "errors": [...], "warnings": []}`).

## Design notes

- Rating mapping, first matching row wins: learner override ("I was right") → Good; `wrong` →
  Again; `almost` (accent, typo, article, or an AI "almost") → Hard; `correct` with a hint → Hard;
  `correct`, no hint, exercise type `pick_meaning` or `match_pairs`, `response_ms` ≤ 2,500 → Easy;
  `correct` → Good. A missing `response_ms` never gives Easy.
- Scheduling: `fsrs::FSRS` with `fsrs::DEFAULT_PARAMETERS` (FSRS-6, 21 values) and
  `next_states(memory, desired_retention, days)`. Days elapsed is whole days,
  `floor((now − last_review) / DAY_MS)`, never below 0, and 0 for a new card (no memory state), as
  FSRS and py-fsrs count them; same-day reviews therefore take FSRS's short-term formula. The crate
  works in f32; stability and difficulty are stored widened to f64, so narrowing them back is exact
  and a replay reproduces them bit for bit. Interval = `min(365, max(1, round(interval)))` days
  from the crate's interval at the desired retention (at 0.90 it equals S); `due = now +
  interval × DAY_MS`. No fuzz.
- Card state after a review: Again → `relearning`, any other rating → `review`; `reps` + 1 on
  every review; `lapses` + 1 when Again is given to a card in state `review`; `last_review` = the
  review time. Without learning or relearning steps the interval rule is the same in every state.
- Retrievability (queue and mastery): the FSRS-6 forgetting curve in f64, R(t, S) = (1 + f·t/S)^(−d),
  d = w[20], f = 0.9^(−1/d) − 1, t the fractional days since the last review (`(now − last_review)
  / DAY_MS`, never below 0); a card without stability has retrievability 0.
- Review log: one row per review, never updated or deleted (invariant I6); `elapsed_days` is the
  whole-day value FSRS received; `stability_after` and `difficulty_after` are the card's new values.
  `replay` starts every (item, facet) of the log from `Card::new` and applies `schedule` to its
  entries in log order; it returns one card per (item, facet) that the log mentions, ordered by
  item id in byte order, receptive before productive. Stability, difficulty, state, counts and
  `last_review` depend on the log alone; `due` also depends on the desired retention, so a replay
  equals the `cards` table (its reviewed cards) when the retention was unchanged.
- Store: `Store::open` takes the path of `parley.sqlite3` from the caller, like packs in module 01
  (SQLite cannot go through the `Fs` trait); foreign keys on. Migrations run in a transaction each;
  the SQL of `0001_init` is §4's DDL for those seven tables and their indexes verbatim, so a file
  that already holds one of its tables fails with `Migration(1)` and is left unchanged. `open` on a
  file with `user_version` above the newest migration refuses with `TooNew`.
- `start_course` (the language is the syllabus's): `courses` keeps its first `started_at` and takes
  the new `syllabus_version`; skills are upserted with `ord` = index in syllabus order and their
  `tested_out` flag kept; a skill gone from the syllabus keeps its row with `ord` −1; items come
  from `derive_items` (`source_kind` `syllabus`, `en` and `lemmas` as JSON arrays); an item gone
  from the syllabus is marked `retired`, one that comes back is active again; the `content` rows of
  `accepted_answers` of the course's items are rewritten on every call (`norm` = NFC lower case of
  `display`; module 03 may change the normaliser), `judge` and `learner` rows are kept. Calling it
  twice with the same syllabus changes nothing but leaves timestamps of the first call.
- `introduce` creates the two `new` cards of an item; `review` introduces an item that has none
  yet, then schedules, updates the card and appends the log row in one transaction. An item id not
  in `items` gives `UnknownItem`.
- Due queue: cards with `due ≤ now` of items not retired in the course's language, ordered by
  retrievability ascending, then `due`, then item id, then receptive before productive; at most
  `limit`. `queue_order` is the same ordering over given cards.
- Mastery of a skill: the sum of retrievability over its cards divided by twice the number of its
  items (not retired), so cards of unintroduced items count 0 (`mastery_of`). States, first that
  holds: **mastered** when practised and mastery ≥ 0.85; **practised** when every item has at
  least one reviewed card; **learning** when at least one item is introduced; **available** when
  every `requires` skill (or, if empty, the previous skill in syllabus order; the first skill
  always) is practised, mastered or tested out; otherwise **locked**.
- Placement (Levitt 1971): skills of the course in syllabus order, indices 0 to N−1. Start at
  `i = N / 4` (integer), `step = max(1, N / 4)`. The question is the skill at `i` (module 04 asks
  its first vocabulary item, translated to English and graded offline; almost counts as correct).
  After an answer, if its correctness differs from the previous answer's, record a reversal at the
  current index and set `step = max(1, step / 2)`; then move `i = min(N−1, i + step)` if correct,
  `max(0, i − step)` if wrong. Stop at 20 questions, or at 12 or more with at least 8 reversals,
  or early after 4 wrong answers in a row at index 0 (a kindness to beginners; below the
  12-question floor on purpose). Estimate: with 3 or more reversals, the mean of the reversals
  after the first two; otherwise the mean of the last 4 question indices; means are rounded half
  up in integer arithmetic, `(2·sum + count) / (2·count)`. N = 0 finishes at once with estimate 0.
  Skills below the estimate are tested out. CEFR label: estimate < 3 → "Pre-A1"; else "around "
  plus the estimate skill's `cefr`.
- At planning, 20,000 simulated learners (boundaries uniform over 0 to 80, slip 0.1) landed within
  ±4 of their boundary about 92% of the time with the 8-reversal stop (90% with 6); slip 0.05 gives
  about 98%. A 200-learner sample therefore asserts 85%.
- `apply_placement`: every tested-out skill gets `tested_out = 1`; each of its items not retired is
  introduced, and each card still `new` gets one review rated Good at the placement time with
  `exercise_type` `placement`, verdict `correct`, no `response_ms` and the given session id;
  `courses.placement_index` and `cefr_estimate` take the estimate and label.
- Simulated learner: one draw per question, `u = (next_u64() >> 11) / 2^53`; the answer
  `index < boundary` is flipped when `u < slip`. SplitMix64 (Steele, Lea and Flood 2014): state +=
  0x9E3779B97F4A7C15, then z ^= z >> 30, z *= 0xBF58476D1CE4E5B9, z ^= z >> 27, z *=
  0x94D049BB133111EB, z ^= z >> 31.
- `local_date`: the clock's milliseconds plus its UTC offset in minutes, floored to whole days,
  turned into a civil date (Hinnant's civil-from-days), so no date library is needed.
- `syllabus-mini` (`tests/fixtures/generated/syllabus-mini/xx/syllabus.yaml`): `lang: es` in a
  folder `xx`, so V02 does not run; 8 units of 10 skills, units 1 to 4 A1 (`es.a1.u01` …
  `es.a1.u04`), units 5 to 8 A2 (`es.a2.u05` … `es.a2.u08`), skill ids `<unit>.s01` … `.s10`, skill
  index = 10 × (unit − 1) + (skill − 1); every skill has `requires: []`, at least 3 lemmas of
  pseudo-words (letters only, not Spanish words) and at least 4 examples made of its own and
  earlier skills' lemmas, so `parley content validate` reports it clean.
- Reference values for FSRS come from py-fsrs 6.3.2 (MIT; `Scheduler` with the crate's parameter
  vector, desired retention 0.9, no learning or relearning steps, maximum interval 365, no fuzz),
  run with `uv`, not from the Rust code. py-fsrs 6.3.2 and fsrs 6.6.2 share the default vector,
  the short-term formula (Hard, Good and Easy at least keep stability) and the unclamped D0(4) of
  mean reversion. The `fsrs` crate is BSD-3-Clause (crates.io, 2026-11-03).
- Decisions made during implementation:
  - `fsrs` is pinned exactly (`=6.6.2`) in the workspace manifest, because the recorded
    reference values were checked against that version; a newer crate is a deliberate upgrade.
  - The interval keeps the crate's f32 value. At 0.90 it differs from S by a few ulps at most:
    of the 32,000 f32 values nearest the half days from 0.5 to 399.5, five round the other way,
    so `round(interval)` and `round(S)` agree for every stability FSRS produces in practice.
  - A card is given to FSRS with a memory state only when stability and difficulty are both
    present and finite; otherwise it is scheduled as new. Days elapsed saturate at `u32::MAX`.
    Retrievability is 0 for a card without a last review as well as without stability.
  - `Rating` reads any JSON integer and refuses one outside 1 to 4 with "rating must be 1, 2, 3
    or 4, not {n}". `SrsParams::with_retention` of NaN gives 0.90; the bounds and the default
    are `SrsParams::MIN_RETENTION`, `MAX_RETENTION` and `DEFAULT_RETENTION`.
  - `ReviewLog::parse` drops a byte-order mark, gives serde's message for a file that is not
    the shape, then checks the schema ("schema must be parley.review-log/1"). Unknown fields
    are ignored; `elapsed_days`, `stability_after` and `difficulty_after` may also be `null`.
  - `queue_order` keeps only cards with `due ≤ now` (a card without a due date is never
    queued), so `due_queue` is the store's filter (language, not retired) plus `queue_order`.
  - The `skills` table has no column for `requires` and `items` none for syllabus order, so
    `start_course` keeps both in `meta` under `skill:<id>` as
    `{"requires": [...], "items": [...]}`; `item_ids` orders by that list, then by insertion.
  - `start_course` retires only `source_kind = 'syllabus'` items of the syllabus's language;
    items from other sources are never retired by a syllabus. `CourseReport.items` is the
    syllabus's item count, `added` counts items not active before the call (new, or back),
    `retired` those it retired, so active after = active before + added − retired.
  - Content accepted answers are reconciled, not deleted and reinserted, so an unchanged answer
    keeps its `created_at`. A content answer whose `norm` already has a `judge` or `learner`
    row is not inserted (that row is kept); of two displays with one `norm` the first in
    syllabus order is kept; retired items lose their content answers.
  - `Store::skills` leaves out skills gone from the syllabus (`ord` −1), so placement never
    asks about them; their `skill:` meta row stays.
  - `introduce` does not store `now_ms` (the 0001 `cards` table has no column for it). `card`
    gives `None` for an item without cards, known or not; `item_ids`, `skill_mastery` and
    `skill_state` give `UnknownSkill` for an id not in `skills`; `is_retired` gives
    `UnknownItem`.
  - `apply_placement` gives `UnknownSkill` for a tested-out id that is not a skill of that
    language, and the whole placement is rolled back. It reviews cards in syllabus order,
    receptive first; a card already reviewed keeps its schedule.
  - Skill states: a reviewed card is one with a last review; a skill whose items are all
    retired is practised (no item lacks a review), so it never blocks the next; a `requires`
    entry the store does not know is not met; the previous skill is the nearest lower `ord`.
  - `Store::open` switches foreign keys on before migrating; a negative `user_version` is
    treated as `TooNew`. `0001_init.sql` opens with a two-line comment before §4's statements.
  - CLI: every flag is checked before any file is read, so `--retention 0.99` on a missing log
    reports the retention; `<log.json>` and `--syllabus` must be files; `--boundary` is a
    non-negative integer, `--seed` an unsigned 64-bit integer, `--slip` from 0 to 1 inclusive;
    a log that is not UTF-8 fails with `error: {path}: not valid UTF-8`.

## Acceptance tests

Golden cases in `tests/cases/02-srs-and-learner-model/`; code tests in
`crates/parley-core/tests/m02_srs_and_learner_model.rs` and
`crates/parley-cli/tests/m02_srs_and_learner_model.rs` (the CLI's usage errors and test 7's
command-line half).

1. Migration on an empty file creates the seven tables with the columns of ARCHITECTURE §4
   (`PRAGMA table_info` compared) and `user_version` 1; a file with `user_version` 99 gives "This
   data file was written by a newer Parley. Update Parley to open it."; a file that already has a
   `meta` table gives "Parley could not update its data file (step 1). Restore a backup or report
   this."
2. `start_course` twice gives the same item count; introducing an item creates exactly two `new`
   cards; a syllabus with one example removed and version 2 marks that item retired and keeps its
   two cards.
3. A new card's first review sets stability to `w[0]`, `w[1]`, `w[2]`, `w[3]` of the crate's default
   parameters for Again, Hard, Good, Easy (tolerance 1e-9; FSRS definition of initial stability).
4. At desired retention 0.90 and no fuzz, every scheduled interval equals `max(1, round(S))` days,
   capped at 365 (1,000 rating sequences from SplitMix64 seeds; FSRS defines S as the interval at
   which recall falls to 90%).
5. The five scenarios in `fsrs_reference.json` (py-fsrs): stability and difficulty after each
   review within relative tolerance 1e-4; the golden case `srs-replay-reference` replays them
   through `parley srs replay` and matches py-fsrs's stability, difficulty and due dates.
6. `rating_for` returns each row of the Design notes table (seven cases).
7. After 500 seeded reviews over 40 items, `replay(review_log)` equals the reviewed cards of the
   `cards` table exactly; `parley srs replay` on the exported log prints the same cards.
8. A fixture of five due cards with known stability and elapsed days is queued in ascending
   retrievability computed from the FSRS forgetting curve at the crate's parameters.
9. A skill of 4 items where 2 items have cards of retrievability 0.9, 0.8, 0.7, 0.6 → mastery
   (0.9 + 0.8 + 0.7 + 0.6) / 8 = 0.375 (tolerance 1e-9).
10. Skill states on `syllabus-mini`: at start skill 0 is available and skill 1 locked; after one item
    of skill 0 is reviewed, skill 0 is learning; after all its items, practised, and skill 1 available.
11. Placement on `syllabus-mini` (N = 80), as a golden case through `parley placement simulate`, with a learner correct exactly below index 23: questions
    at 20, 40, 30, 20, 25, 23, 21, 22, 23, 22, 23, 22; reversals 40, 20, 25, 21, 23, 22, 23, 22;
    estimate round(136 / 6) = 23; 12 questions; skills 0 to 22 tested out; label "around A1".
12. Boundary 0 → questions at 20, 0, 0, 0, 0; stops after 5; estimate 0; label "Pre-A1". Boundary
    80 → 20 questions ending at 79; estimate 79; label "around A2" (the mini syllabus's last skill is A2).
13. 200 seeded learners with slip 0.1 and boundaries uniform over 0 to 80: ≥ 85% of estimates
    within ±4 of the boundary; every run asks 12 to 20 questions or exits early at index 0.
14. Tested-out cards each have one log entry with `exercise_type` "placement" and rating Good, and a
    due date `round(w[2])` days after the placement time.
15. `local_date` with the clock at 2026-03-29T00:30Z: offset +60 → 2026-03-29; offset −300 → 2026-03-28.
16. No source file under `crates/` contains `UPDATE review_log` or `DELETE FROM review_log`
    (append-only, invariant I6).
17. SplitMix64 with seed 0 yields 0xE220A8397B1DCDAF, 0x6E789E6AA1B965F4, 0x06C45D188009454F
